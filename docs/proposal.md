# 모잇(Moit) 제안서

실행 작업과 진행 상태는 [GitHub Project](https://github.com/orgs/capstone-30/projects/1)에서 관리한다.

## 제안 요지

같은 학교 학생끼리 관심 주제가 맞는 사람을 찾아 가능 시간에 모각공·커피챗·런치챗을 여는 서비스다. 혼자 공부하다 막히는 상황, 공강·점심의 동료 부재, 재학 선배와의 진로 접점 부족을 해결하려 한다. 모집과 시간 조율을 오가다 만남이 끊긴다는 문제 가설에서 출발한다.

대상은 학과·동아리 안에서 관심사가 맞는 동료를 찾기 어려운 재학생이다. 구조는 다양한 주제를 지원하되 첫 학기는 단일 캠퍼스의 개발·IT 학습에 집중한다. 공강은 수업이 없는 시간이 아니라 모임 제안을 받아도 되는 시간이며, 한 번 등록해 재사용하되 모임별 예외를 허용한다.

학습 지속, 진로 접근성, 학과 간 교류 증가는 기대 효과다. 인터뷰·사용자 관찰·수요 조사 전까지 검증된 효과로 주장하지 않는다.

## 사용자 흐름과 화면 초안

학교 이메일 인증 → 가능 시간 등록 → 주제별 모임 개설·참여 → 교집합 또는 시간 제안·수락으로 확정 → 참여자 코멘트로 연락 → 만남 → 재참여.

기능·안전은 [MVP 요구사항](../spec.md#요구사항), 우선순위는 [GitHub Project](https://github.com/orgs/capstone-30/projects/1), 화면별 목적·관련 FR·빈 상태·로딩·실패는 [화면 설계](../plan.md#개정-화면-설계)를 따른다. 학기별 시간 등록은 매 모임의 참여 승낙이 아니다. 코멘트는 실시간 채팅 대신 새로고침 기반으로 제공한다.

## 차별점과 경쟁 조사


| 비교 대상                          | 확인할 기존 방식·한계 가설                       | 모잇의 제안                           |
| ------------------------------------ | --------------------------------------------------- | --------------------------------------- |
| 에브리타임·학교 게시판·학과 단톡 | 모집 이후 별도 연락과 조율, 관심사 대상 도달 한계 | 주제별 모집과 시간 조율 연결          |
| 카카오톡 오픈채팅·디스코드        | 캠퍼스·공강 맥락의 오프라인 만남 조율 부담       | 같은 학교 인증과 학기별 가능 시간     |
| when2meet                          | 모임별 링크·가능 시간 재입력                     | 학기별 재사용과 모임별 예외           |
| 문토·소모임                       | 캠퍼스 재학생의 짧은 공강 모임에 맞는지 확인 필요 | 이미 캠퍼스에 있는 학생의 소규모 만남 |

실제 기능·가격·대상 범위 비교는 T2 조사 전 미확인이다. 모든 경쟁 서비스가 유료이거나 오프라인 기능이 없다고 단정하지 않는다. 핵심 차별 가설은 시간 미정 모집, 가능 시간 재사용, 모집·조율·후속 연락의 연결이다.

## 초기 사용자 확보

- 단일 캠퍼스에서 50명 확보를 목표로 교내 부서·학과 공지·비교과 채널 접촉을 우선 시도하고 GDGoC·개발/IT 동아리·관련 학과 단톡을 활용한다. 접촉·확보 실적은 아직 없다.
- 첫 2주 동안 팀원 4명이 매주 최소 3건의 모임을 직접 개설하는 운영안이다. 팀 전체/개인별 할당은 확정해야 한다.
- 빈 목록에서는 모임 개설을 안내한다. 주제 수요 수집·동일 주제 3명 알림은 [범위 결정](../spec.md#범위)에 따라 이번 프로젝트에서 제외한다.
- 주간 활성 모임 10건이 2주 연속 유지되면 어학·자격증, 이후 취미로 주제를 넓힌다. 활성 정의와 측정 방법은 미확정이다.

## 비즈니스 모델

학생에게 모든 기능을 영구 무료로 제공한다는 정책안이다. 프로젝트 기간 과금은 없으며 아래 구매 수요·효과·일정은 검증 전 가설이다. 기관 계약이나 카페 제휴는 확보하지 않았다.


| 단계·대상       | 제공 가치·방식                                                                       | 전환 조건·검증                                                                |
| ------------------ | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 프로젝트 기간    | 사용 지표 검증, 여유시 기관 대시보드 시연                                             | 합성 데이터 시연만 허용, 실사용자 집계 제공 제외                               |
| 1년 내 대학 기관 | 교수학습개발원·비교과통합센터·학생상담센터 등에 연 단위 서비스와 집계 대시보드 공급 | 캠퍼스 1곳 주간 활성 모임 10건 유지, 담당 부서 구매 의사·예산·계약 단가 검증 |
| 2년 내 기업      | 현직자와 학생의 스폰서 커피챗에 세션 단위 과금                                        | 개발·IT 전공 사용자 500명 이상, 기업 수요·전환 효과 검증                     |
| 카페 쿠폰        | 확정 모임의 참석 유도·노쇼 감소                                                      | 실제 제휴 확보·성사율 효과 검증. 카페 노출료·수수료를 수익원으로 두지 않음   |

장기 기관 상품은 주간 활성 모임 수·학과 간 교류·신입생/편입생 참여·반복 참여 등의 집계를 검토한다. 이번 프로젝트의 기관 화면은 합성 데이터만 사용하며 [개인정보 정책](../spec.md#개인정보운영-정책)을 따른다. 현재 프로필만으로 편입 여부를 알 수 없으므로 지표별 수집 필요성과 최소 수집을 검토해야 한다. 학교 브랜딩을 최소화하고 개인 활동 감시로 이어지지 않도록 한다. 학교 도입 채널은 초기 확보에 도움이 될 수 있으나 계약 한 건이 사용자를 보장하지는 않는다.

스폰서 세션은 별도 탭·명시 표기·비중 상한을 두는 장기안이다. 현직자 참여와 4~6인 세션은 현재의 재학생·2~4인 범위 밖이므로 별도 인증·정원·시간 설계가 필요하다. 이번 MVP에 그대로 포함하지 않는다.

쿠폰은 수익 기능이 아니라 성사율을 높이려는 수단이다. 현재는 여유시 시연 데이터만 허용하며 실제 제휴 없음 표시가 필요하다. 확보 전 상시 제공을 약속하지 않는다.

## 성공 기준과 검증

사용자 확보·활성 목표는 위 초기 사용자 확보의 가설이며 측정 정의·방법은 미확정이다. 제품 완료 판정은 [완료 기준](../spec.md#완료-기준)을 따른다. 실제 사용자 테스트 전 목표를 성과로 표기하지 않는다. 참석 체크와 기관 대시보드는 [범위 결정](../spec.md#범위)에 따라 여유시로 확정했다.

## 브랜드 표현

전체 화면은 기존 색상을 유지하면서 직관적인 스타일로 통일한다. 정보 위계·공통 컴포넌트·화면별 적용 기준은 [디자인 기준](design.md)을 따른다.

학습 동료를 찾고 시간을 맞추는 서비스에 선명한 파랑과 부드러운 밝은 바탕을 사용한다. 역할별 색상·선정 이유와 두 사람이 연결된 m 형태의 앱 아이콘은 [브랜드 기준](brand.md)을 따른다.

## 기술 구성

Next.js·TypeScript 단일 앱과 AWS Lightsail·관리형 PostgreSQL·SES로 구성한다. 선정 근거·비용·환경 분리·운영 조건은 [기술 스택](../plan.md#기술-스택), 수집·보관·삭제 기준은 [개인정보 정책](../spec.md#개인정보운영-정책)을 따른다. 실제 연동·배포는 미완료다.

저장소 배치는 [저장소 구조](../plan.md#저장소-구조)를 따른다. MVC 패턴으로 Model의 데이터·업무 규칙, View의 화면, Controller의 요청 처리를 분리한다. 화면과 책임별 구현 원본은 [MVC 설계](../plan.md#mvc-설계), 데이터 관계·요청/응답·권한은 버전 SQL과 REST Controller 구현을 따른다. 대안 확정 후 시간 변경은 [확정 정책](../spec.md#대안-확정-후-시간-변경-정책)을 따르며, 코드 반영은 [남은 작업](../plan.md#남은-운영-연결)이다.

## 개발·발표 계획

조사·범위 확정 → 설계·구현 → 사용자 검증 → 발표·데모로 진행한다. 전체 작업 기간은 확정했으며 원문의 3주 가정을 대체한다. 기간과 단계별 일정은 [단계별 계획](../plan.md#단계별-계획)에서 관리한다. 팀 역할·공식 제출 조건·조사 근거를 확보한 뒤 제출본으로 확정한다.

발표는 문제 → 경쟁 방식·차별 가설 → 핵심 흐름·안전 설계 → 기관 중심 BM → 실제 검증·한계 순서로 구성한다. [완료 기준](../spec.md#완료-기준)을 따르며 모든 MVP 기능을 데모에 포함한다.
